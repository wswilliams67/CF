S-1 Answered B · B2 · C · D

Can a legal hold be inherited by the person a split creates?

PM ruling · 09-01-2026 “Yes, because the new person might be the right person. The original person put on legal hold could have been wrong because the correct person was part of an errant merge. But, the original person (if they survive) should not ever be automatically removed from the legal hold. That could only happen in either the workflow attribution process or by actually releasing the person from the hold.”

Split's screens were already correct. B, B3, B4 and B5 show the hold on both people, and B1, B2, C and D show it inherited onto the new person. Nothing needs redrawing.

And this does not contradict merge. PRD D-3 refuses a merge under an active hold; split inherits. That reads as a contradiction until you see what each does to custodian identity — a merge removes a custodian, a split only adds one. Refusing the destructive case and inheriting on the additive one is one consistent policy, not two. The Merge board's sticky has been corrected to say so.

New constraint, not yet drawn: “should not ever be automatically removed” needs to be visible somewhere. Today no screen claims the original loses its hold — but none states that it keeps it either, and the two named exits (workflow attribution, explicit release) appear nowhere in the split flow. This is the follow-up work S-1 creates.

S-2 Answered B3 · B4

Must every case be attributed before the split can be applied?

PM ruling · 09-01-2026 “Yes, every case should be attributed. Follow house rule. It might cause delays for the operator, but that is much better than having a decision be automated that goes unnoticed.”

Option B. APPLY ATTRIBUTIONS stays disabled until every case is set, matching the house rule that a primary is disabled until the form validates. The screens currently draw it enabled, so B3 and B4 both need the disabled state adding.

Still to confirm: the panel has no empty state. A person on no cases has nothing to attribute, so CHOOSE WORKFLOW ATTRIBUTIONS should probably not be offered at all — otherwise the house rule produces a dialog that can never be satisfied.

S-3 Needs restating Edge §7

In shadow mode, is Split hidden or shown-disabled?

PM reply · 09-01-2026 “I don't know what this means. What is shadow mode?”

Fair — the term is ours, not the product's. It appears exactly twice in the whole file, both times as a layer name, and never in any interface copy. On the edge-states board it is case 9, and the screen says: “9 · Ledger in shadow mode / No projection authority / UNAVAILABLE” with the note “The whole action is unavailable with an explanatory state — not a button that fails when pressed.”

In plain terms: a deployment where CaseFusion is reading the identity ledger but has no authority to write the projection — running alongside an existing system rather than owning the data. Nothing can be split, because the split cannot be applied.

The real question, restated: does that deployment mode actually exist, and is it a state this tenant can be in? If yes, the design question stands — hide the action, or show it disabled with the reason. If nobody can say what puts a tenant into it, this edge case may be describing a mode that was never built, and it should be struck rather than designed around. That is an engineering question first, not a product one.

Either way the term does not survive. “Shadow mode” is not in the controlled lexicon and would not pass a conformance scan. If the state is real it needs a user-facing name; the screen already avoids it, saying only that the action is unavailable.

S-10 To draw B3 · B4

Show who to ask about a case

PM request · 09-01-2026 “We need to either make the case name have a hover state with more info or show more on the single case workflow attribution screen. At a minimum, I think we should show case owner and primary counsel (if populated). That will give the operator the correct contact person if they need to ask a question about attribution.”

Two options, and they are not equivalent.

  • AHover on the case name — works on the all-cases screen (B3) where rows are dense, but hover is not available on touch and is not keyboard-reachable without extra work. It also hides the very thing that unblocks the operator behind a gesture they have to discover.
  • BShow it inline on B4, the per-case screen — there is room, the operator is already looking at one case, and it needs no gesture.

Recommendation: B, and A only if B3 also needs it. The PM's reason is that the operator may need to ask someone a question — that is a moment where they have stopped and are deciding, which is B4's situation, not a scan down B3. If B3 needs it too, a row-expand is more robust than hover.

“if populated” matters. Both fields can be empty, and an empty contact is worse than none — it reads as though nobody owns the case. Absent fields should be omitted, and if both are missing the panel should say plainly that no contact is recorded rather than showing two blank labels.

Questions for engineering

Not decisions — facts about what already exists. Each one changes what the interface is allowed to promise, so the answer shapes the build either way.

S-4 High B

Is a dry-run rebuild available?

The entire preview assumes we can retract hypothetically and get the resulting projection back without committing. #17378 verifies a real retraction and rebuild; no hypothetical path is called out anywhere.

Without one the interface can only offer a button whose effect it cannot describe — on the operation that exists to correct irreversible mistakes.

Fallback if the answer is no: commit-then-undo, which inverts the preview-before-consequence pattern used everywhere else in this feature set. Workable, but it is a different design, not a smaller one.

⏱ Timing — retrofitting a dry-run onto a projection builder written only to commit is materially harder than building it in. This needs answering while #17377 is in flight.

S-5 High Foundation · C

Are assertions individually retractable — and is a retraction itself an appended assertion?

The whole model rests on this. “Recorded, not erased” on screen C, and the history claim on both resulting people, depend on the ledger appending a retraction rather than deleting a row.

If the ledger deletes instead: screen C’s central promise is false and the audit story for a split has to be rewritten before anything is built.

S-6 High A

Is an operator-asserted join supported, and is it distinguishable from a key-derived one?

Move to a specific person is a retraction plus a manual join. Two parts: can the ledger record that at all, and can a later reviewer tell a human decision from a machine match?

Why the second half matters as much as the first: if the two are indistinguishable in the record, every operator-moved identity looks like the matcher’s work when the log is read back — which is exactly the question a declaration would be asked.

S-7 Open D

Is the rebuild synchronous per person, or queued?

Determines whether the After state shows a progress indicator at all.

Why it is not cosmetic: pfizerpoc holds 61,888 persons, so a rebuild may not be instant. A person page showing a stale projection with no indication is worse than one that says plainly it is rebuilding.

S-9 New · raised by S-8 A · B2 · #17515

When the system chooses the destination, does the operator ever see it?

PM question · 09-01-2026 “If that is done via the ‘let the system decide’ option, though, is that shown to the operator or would that proposed merge go back into the queue for adjudication? It can have consequences, and while it may be the correct outcome, a human needs to know about it.”

Two candidate answers, and they are materially different builds:

  • AShown in the preview. B2 already names the destination person, so the operator sees and accepts it before confirming. Nothing new is queued. Simplest — but it makes a re-home a decision the operator takes on the spot, with whatever context that one screen carries.
  • BRaised as a pending match. The split proceeds and the proposed convergence goes to the Pending Match Queue (#17515) for adjudication, exactly like any other refused-but-plausible pair. Slower, but the decision lands where every other identity decision is recorded, with the same evidence and the same audit trail.

Why this is worth answering carefully: B is the only option where the re-home is recorded as a decision by a named person. Under A it is recorded as part of a split, and a later reader cannot easily tell that a convergence happened at all. The PM's own framing — “a human needs to know about it” — points at B, but B means Split can produce queue work, which nothing on either board currently shows.

Not drawn either way. If B, Split needs a state saying the re-home was queued rather than applied, and #17515 needs to show where such a pair came from.
