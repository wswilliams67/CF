First Run — tenant onboarding

First Run is one journey across three sign-ins by the same person. Stage 1 hands the tenant from the provisioning account to a named Tenant Administrator. Stage 2 connects the integrations. Stage 3 configures the tenant and lets the user into the application. This pass walks all three in order, then the cross-cutting rules that apply on every screen.

This is a UI functionality pass, to be run once the code is built. The design was handed off as specification only — no prototype and no reference implementation — so every check here is written against the built screens, not against a mock. Section K covers motion, which is the part most likely to be approximated rather than matched.

Every expected value below was read off the Figma board First Run [Claude v2] on 09-25-2026, not from memory. Counts, copy, hex values, toast wording and animation timings are quoted exactly so a wrong-but-plausible result gets caught rather than waved through.

Tick as you go. Ticks are saved in this browser, so you can stop and come back.

Before you start

Build URL
Not yet built — fill in at handoff. Use the published review site address, never localhost.
Spec
Figma · First Run [Claude v2] — 207 screens, 241 Dev Mode annotations (209 Development, 27 Interaction, 5 Animation). Screen letters below (2F16, 3D5) are the frame names on that board.
Three sign-ins
Stage 1 as the Provisioned Administrator; Stages 2 and 3 as the Tenant Administrator they invite. You will need both sets of credentials and a mail box that receives the invitations.
Tenant state
A fresh tenant that has never completed First Run. Completing or skipping sets a tenant-level flag and the journey never appears again, so a used tenant cannot be retested without a reset.
Viewport
1440 wide or more. The Email Templates dialog is sized to the viewport and the Microsoft 365 service rows need the width.
Theme
The board is drawn dark. Run the pass in dark, then repeat check J8 in light.
Motion
Section K needs browser DevTools — the computed transition on the animating element, and the prefers-reduced-motion emulation. Values are the Nimbus styleguide's; the file each comes from is named in the check, so a disagreement is settled by reading the styleguide rather than by eye.
Several integrations are live third-party dependencies. Microsoft 365 consent, Expireon, Active Directory agent installation and Truto all reach systems outside CaseFusion. If one is unavailable, record its section as blocked rather than failed — a rejection path (2F16) is a legitimate test, an unreachable service is not.
Microsoft 365 admin approval cannot be faked. Check D10 needs a real Microsoft administrator to approve a consent request. If none is available, stop after E6 and mark the rest blocked.
A

Stage 1 — handing over the tenant

Stage 1 exists only to replace the shared provisioning credential with a named person. One Required task and nothing else.

B

Stage 2 — administrators

Signed in now as the Tenant Administrator invited in Stage 1. Stage 2 has three categories — Required, Integrations, Optional — and only one Required task.

C

Active Directory and Expireon

Both integrations happen entirely inside their own card — no dialogs. Active Directory runs four numbered steps; Expireon separates testing from connecting.

D

Microsoft 365

One card holding seven service rows. Contacts are captured once at the top and gate every row. Each service is independent — connecting one must not touch the others.

E

Truto

Truto is a broker — CaseFusion connects once to Truto and Truto reaches the HR and messaging systems beyond it, Slack included. Connecting a system and scheduling its sync are separate steps.

F

Stage 3 — the two Required contacts

Legal Team Contact and Support Contact are a fixed set of field values, not lists, so they are inline forms in the card with their own Cancel and Save.

G

Stage 3 — the list tasks

Case Categories, Users, Properties and Tags share one pattern: a card list, a dialog that stages entries as removable chips, then one commit. Run G1–G8 against each of the four and record a result per task.

H

Email Templates

The one list task that breaks the shared pattern. A template holds a written message, so there is one template per dialog — no chips, no bulk save — and rows keep an Edit action.

I

Escalation Settings, and finishing

Four interval values, then the end of the journey.

J

Rules that apply on every screen

These hold across all 207 screens. Spot-check each on three or four screens drawn from different stages rather than walking them all.

K

Motion

Every value below is the Nimbus styleguide's, not a design invention — the source file is named in each check so a disagreement can be settled by reading it. Nothing here needs a stopwatch: read the computed style in DevTools, or watch for the described behaviour.

L

Known deviations and open items

Read these before filing anything in them as a defect.
