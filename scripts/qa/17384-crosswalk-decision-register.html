C-1 High Default · Export

Does an export contain the columns you can see, or all of them?

The toolbar's COLUMNS control sets what the table displays. The export modal sets what the file contains. They are separate today, so an operator can hide three columns, export, and find all of them in the file — which will be read as a bug rather than a design.

Proposal: the export defaults to the visible column set, so the choice is made once, in the place the operator already made it. They can still override it in the export modal.

Either ruling is now safe to build against. The Export detail panel records the actual column set per run — Columns: Source record, Source, Natural person, Linked by, How, When — so the ambiguity does not survive the export whichever way you answer. What your answer decides is what the operator sees at export time.

C-2 Blocking Save view · Load view · delete confirmation

Is a saved view personal, or shared across the tenant?

Nothing in the flow says whose views these are. No owner appears on any row, which reads as "personal" by implication — but it was never decided, and three things depend on it.

It decides whether rename exists at all. A personal view can be renamed freely. A shared one carries somebody else's name in somebody else's workflow, and renaming it silently changes what a colleague is looking for.

It decides who gets DELETE. Today every row has it. If views are shared, one operator can delete a view another operator built and relies on.

And it decides the confirmation copy. The dialog currently says the view is gone and cannot be undone. If views are shared, that sentence is doing far more work than it appears to, and should say whose view is being removed and who else loses it. This is why C-2 blocks: the copy cannot be written until the answer is known.

C-3 High Exports · Export detail

How long does a generated export file stay downloadable?

The board states a retention window it was never given. Rows read Ready — expires in 2 days and Ready — expires tomorrow; two rows already show Expired with RUN AGAIN in place of Download. Those are drawn from an assumption.

The window sets the expiry on every row and in the detail panel, and it decides a behaviour nobody has specified: what happens when Download is pressed on a job that expired while the list was open. Engineering needs to confirm what the storage actually does, but the window itself is a policy call.

C-4 High whole section

How does anyone reach the crosswalk?

There is no route to it from the product. The only link in the file comes from Unmatched Source Records — and that surface's own sticky says nothing links to it either, and that its top-level placement "is an assumption, not a decision".

Three candidates. A nav entry under Administration; from Legacy Data Import completion, which EXPERIENCE.md already names as the entry point for remediation; or from Unmatched Source Records, once that one has a route of its own.

Answer this with the Unmatched question, not after it. Option 2 on the Unmatched sticky proposes reaching Unmatched via the crosswalk. That cannot be the answer while the crosswalk is itself unreachable, so answering them separately risks a circular route. Whichever way it goes, the page title gains a back control naming its origin, and the screens stop being top-level.

C-5 Blocked · DM then PM not drawn

The decision export cannot be drawn — two stories contradict each other

Part 1 assigns the decision export to #17384: who decided what, and when. Its column set runs straight into a conflict. #17384 asks for the joining key type and value. #17515 states that matched values are hashes that must never be displayed. Both cannot hold.

The rule is still live even though the sentence went away. The footnote that said so — "Key types only — matched values are hashes and are never displayed" — was removed from #17475 and #17515 on 09-01-2026 as redundant, because those screens never show a value. An export is the one place that would, so removing the note did not remove the constraint. A ruling is needed before the screen exists.

C-6 To draw Default · Load view

A loaded view has no active state, and no modified state

Loading a view applies its filters, sort and column set, then closes the modal. From that moment the crosswalk looks exactly as it would if the operator had set those filters by hand — nothing names the view that is running.

Which leaves the follow-on question undrawn: when the operator then changes a filter, is the view modified? Does the toolbar offer to update it, silently detach from it, or keep showing its name while no longer matching it? There is also no "update this view" anywhere — Save view only ever creates. Three states are missing: view active, view modified, and update-in-place.

C-9 Closed by design Export detail

The Exports list logged the job, but never what the export was

The sticky raised four gaps: Scope: Current filter was unrecoverable after the fact; no row named who ran it; the column set was not recorded; and the failure reason lived behind an Ok button with nothing to return to.

All four are now in the Export detail panel. It carries the resolved filter rather than the label — Scope, Source, Linked by, How, Decider, Date range, Records — plus the column set, Run by: S. Wills · started 2:41 PM, finished 2:47 PM, the file name and expiry, and the failure reason as a record rather than a dialog.

The panel is read-only by design: the row's own action — Download, Resume, Retry, Run again — stays on the row.

C-10 Closed Default toolbar

The Exports list had no route in

It could be reached only by running a new export — Default → Export → Export in progress → Exports — so checking whether last week's export finished meant starting another one.

An EXPORTS LIST secondary button now sits in the toolbar beside EXPORT. It needed a second action slot on Nimbus/Toolbars, which was added to v1 and v2, the styleguide, 1.6 and 2.0, and has been published and accepted.

C-11 Closed Exports

The Export detail panel had no trigger

Every row action was specific — Download, Resume, Retry, Run again — and none of them opened the panel, so the screen it led to was unreachable.

The timestamp in each row is now the link. A VIEW button was considered and ruled out: Nimbus/ListGroup exposes a single Show Action slot, so a second button would have meant a library change across five trees. The timestamp is the row's identifier, and the crosswalk table already links its record ids the same way.
