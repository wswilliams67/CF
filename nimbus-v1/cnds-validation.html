    Validation

    Nimbus™ form validation surfaces error messages inline beneath each field using the HTML5 constraint validation API. Adding .is-invalid to the correct element reveals a .cf-input-error message through CSS alone — no additional JavaScript is needed to show or hide individual messages — keeping layout stable and error presentation consistent across all form components.

    Validation state is applied on submit: a single handler iterates each field, calls checkValidity(), and toggles .is-invalid on the appropriate wrapper or input element. Apply .is-invalid to the .cf-input-field wrapper for standard text inputs, directly on .form-control for input-group fields, and on .form-check-input for checkboxes and radios.

    Note: Use custom validation styles rather than browser-native defaults. Native error tooltips are announced inconsistently by assistive technologies across browsers — particularly Chrome on desktop and mobile — and cannot be styled to match the design system.

    Note: Read the API Documentation to find all available options and advanced customization.

    Note: To preview components in different themes, click the theme toggle button / in the header navigation bar.

    JAVASCRIPT

                              
// Validate all .needs-validation forms on submit
(() => {
  'use strict';
  const forms = document.querySelectorAll('.needs-validation');
  Array.from(forms).forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault();
      event.stopPropagation();

      // cf-input-field inputs — toggle .is-invalid on the wrapper, aria-invalid on the input
      form.querySelectorAll('.cf-input-field .cf-input-control').forEach((input) => {
        const invalid = !input.checkValidity();
        input.closest('.cf-input-field').classList.toggle('is-invalid', invalid);
        input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
      });

      // Input-group form-control inputs — toggle .is-invalid on cf-input-field wrapper if present, else on the input directly
      form.querySelectorAll('.input-group .form-control').forEach((input) => {
        const invalid = !input.checkValidity();
        const cfWrapper = input.closest('.cf-input-field');
        if (cfWrapper) {
          cfWrapper.classList.toggle('is-invalid', invalid);
        } else {
          input.classList.toggle('is-invalid', invalid);
        }
        input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
      });

      // Checkboxes and radios — toggle .is-invalid on cf-input-field wrapper if present, else on the input directly
      form.querySelectorAll('.form-check-input').forEach((input) => {
        const invalid = !input.checkValidity();
        const cfWrapper = input.closest('.cf-input-field');
        if (cfWrapper) {
          cfWrapper.classList.toggle('is-invalid', invalid);
        } else {
          input.classList.toggle('is-invalid', invalid);
        }
        input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
      });
    }, false);
  });
})();

    How it works

    Nimbus™ validation is purely state-driven: adding .is-invalid to the correct element reveals error text; removing it clears the error. No extra JavaScript is needed to show or hide individual messages — CSS handles the reveal once the class is toggled. Here is how .is-invalid maps to each component type:

    • Text inputs and textareas — apply .is-invalid to the .cf-input-field wrapper. The .cf-input-error element inside .cf-input-helper is hidden by default and becomes visible only when the wrapper carries .is-invalid. Input borders and backgrounds do not change — only the error message is revealed.
    • Input groups — wrap the .input-group inside a .cf-input-field and apply .is-invalid to that outer wrapper. Error display follows the same mechanism as for text inputs: the .cf-input-error inside .cf-input-helper is revealed when the wrapper is invalid.
    • Checkboxes and radios — apply .is-invalid to the .form-check-input element to reveal a sibling .invalid-feedback element and switch the associated label to the danger color. Alternatively, wrap the .form-check in a .cf-input-field and apply .is-invalid to the wrapper to use the .cf-input-error pattern instead.
    • Resetting errors — for AJAX or single-page submissions, remove .is-invalid from all wrappers and inputs and clear any aria-invalid attributes after a successful response to return the form to its default clean state.
    • Custom messages — use setCustomValidity() in JavaScript to override the browser's built-in validity message with your own text, or use the constraint validation API directly to compose more complex multi-field validation logic.

    Server side

    When a form POST fails server-side validation and the page re-renders, apply .is-invalid directly in the HTML markup — no JavaScript required. For text inputs and input groups, add .is-invalid to the .cf-input-field wrapper and include a .cf-input-error span inside .cf-input-helper for the error message. Also set aria-invalid="true" on the invalid input so assistive technologies announce the field as erroneous. Fields that passed validation need no extra markup.

    Customizing

    Validation colors are controlled by four CSS custom properties defined in the theme files — a text color and a border color for each of the invalid and valid states. Override any of these tokens in your own stylesheet, loaded after the Nimbus theme files, to update validation colors globally without touching component CSS directly.

    CSS

                              
/* Light theme defaults (defined in css/themes/light.css) */
[data-cnds-theme="light"] {
  --cnds-form-invalid-color: var(--cnds-semantic-danger-400, #db3a00);
  --cnds-form-invalid-border-color: var(--cnds-semantic-danger-400, #db3a00);
  --cnds-form-valid-color: var(--cnds-semantic-success-400, #439945);
  --cnds-form-valid-border-color: var(--cnds-semantic-success-400, #439945);
}

/* Dark theme defaults (defined in css/themes/dark.css) */
[data-cnds-theme="dark"] {
  --cnds-form-invalid-color: var(--cnds-semantic-danger-200, #ff9670);
  --cnds-form-invalid-border-color: var(--cnds-semantic-danger-200, #ff9670);
  --cnds-form-valid-color: var(--cnds-semantic-success-300, #69be6b);
  --cnds-form-valid-border-color: var(--cnds-semantic-success-300, #69be6b);
}

    These tokens flow into every validation-related rule in the component stylesheet. Changing --cnds-form-invalid-color updates .cf-input-error text, .invalid-feedback text, and the .form-check-input.is-invalid label color simultaneously. The companion token --cnds-form-invalid-border-color controls any border or outline applied to invalid input elements.

    API Documentation

    Introduction

    Nimbus™ form validation is state-driven and CSS-first. Toggling .is-invalid on the correct element reveals error text through CSS alone — no JavaScript is required to show or hide individual messages. JavaScript is only needed when validation is performed client-side (e.g., on form submit) to programmatically set .is-invalid and aria-invalid. Server-side validation can apply these classes directly in the rendered HTML without any script. Validation colors adapt automatically to the active theme via four CSS custom properties.

    CSS classes

    The following classes compose the validation markup. All error-reveal behavior is CSS-only — no JavaScript is required to show or hide messages.

    Class Element Description
    .cf-input-field <div> Root wrapper for text inputs, textareas, and input groups. Receives .is-invalid to trigger the error state.
    .cf-input-field-casefusion <div> Product color modifier applied alongside .cf-input-field. Sets the input focus and label accent color for the CaseFusion product. Replace with -hyperlize or -expireon for those products.
    .cf-input-wrapper <div> Inner wrapper that holds the <input>, <textarea>, or .input-group element.
    .cf-input-label <label> Styled label paired with the input control via for / id.
    .cf-input-control <input>, <textarea> The native form control element inside .cf-input-wrapper.
    .cf-input-helper <div> Container placed after .cf-input-wrapper. Holds the .cf-input-error span. Hidden by default; rendered in layout so it does not cause reflow when it becomes visible.
    .cf-input-error <span> Error message text inside .cf-input-helper. Hidden by default; becomes visible when the ancestor .cf-input-field carries .is-invalid. Should carry an id matching the input's aria-describedby.
    .cf-input-required <span> Visual asterisk indicator for required fields. Always paired with aria-hidden="true" — the required attribute on the input conveys the required state to assistive technologies.
    .is-invalid .cf-input-field, .form-check-input State class. Applied to the .cf-input-field wrapper to reveal the .cf-input-error message, or directly to .form-check-input to reveal a sibling .invalid-feedback element and apply the danger label color.
    .invalid-feedback <div> Error message for standalone checkboxes and radios (without a .cf-input-field wrapper). Revealed when the sibling .form-check-input carries .is-invalid.

    CSS custom properties

    All four validation tokens are defined in the theme files and cascade into every validation-related rule in the component stylesheet. Override them in your own stylesheet — loaded after the Nimbus theme files — to update validation colors globally.

    Property Scope Description
    --cnds-form-invalid-color [data-cnds-theme] Text color applied to .cf-input-error, .invalid-feedback, and the .form-check-input.is-invalid label.
    --cnds-form-invalid-border-color [data-cnds-theme] Border or outline color applied to invalid input elements.
    --cnds-form-valid-color [data-cnds-theme] Text color for valid feedback messages.
    --cnds-form-valid-border-color [data-cnds-theme] Border or outline color applied to valid input elements.

    Theme variables

    Validation tokens are overridden per-theme in light.css and dark.css. The invalid tokens meet WCAG AA contrast requirements in both themes. The valid color in light mode falls below the 4.5:1 AA threshold for normal text — pair it with a non-color success indicator (such as an icon or label) to avoid relying on color alone.

    JavaScript

    No JavaScript initializer is required. To perform client-side validation on form submit, loop over each field type, call checkValidity(), toggle .is-invalid on the appropriate element, and set aria-invalid on the input. Add novalidate to the <form> to suppress browser-native tooltips while keeping the constraint validation API active.

    JAVASCRIPT
    // cf-input-field inputs — toggle .is-invalid on wrapper, aria-invalid on input
form.querySelectorAll('.cf-input-field .cf-input-control').forEach((input) => {
  const invalid = !input.checkValidity();
  input.closest('.cf-input-field').classList.toggle('is-invalid', invalid);
  input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
});

// Input-group inputs — prefer cf-input-field wrapper; fall back to input directly
form.querySelectorAll('.input-group .form-control').forEach((input) => {
  const invalid = !input.checkValidity();
  const cfWrapper = input.closest('.cf-input-field');
  if (cfWrapper) {
    cfWrapper.classList.toggle('is-invalid', invalid);
  } else {
    input.classList.toggle('is-invalid', invalid);
  }
  input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
});

// Checkboxes and radios — prefer cf-input-field wrapper; fall back to input directly
form.querySelectorAll('.form-check-input').forEach((input) => {
  const invalid = !input.checkValidity();
  const cfWrapper = input.closest('.cf-input-field');
  if (cfWrapper) {
    cfWrapper.classList.toggle('is-invalid', invalid);
  } else {
    input.classList.toggle('is-invalid', invalid);
  }
  input.setAttribute('aria-invalid', invalid ? 'true' : 'false');
});

    To reset a form after a successful response, remove .is-invalid from all wrappers and inputs and set aria-invalid to "false" on each input.

    Accessibility

    The following attributes are required for an accessible validation implementation:

    • Add novalidate to the <form> to disable browser-native error tooltips. Native tooltips are announced inconsistently by assistive technologies and cannot be styled to match the design system.
    • Set aria-invalid="true" on every invalid input when the error state is applied, and reset it to "false" when the error is cleared. This is the primary signal assistive technologies use to announce the field as erroneous.
    • Add aria-describedby on the input, referencing the id of the .cf-input-error or .invalid-feedback element. Screen readers announce this message when the field receives focus.
    • Apply required to all required inputs. This signals the field's required status to assistive technologies independently of the visual asterisk.
    • Add aria-hidden="true" to every <span class="cf-input-required">. The required attribute already conveys the required state — the asterisk is purely visual.
    • For radio groups, add aria-describedby referencing the shared error element on every radio in the group, so the error is announced regardless of which radio receives focus.

    For the full specification, see the WAI-ARIA specification for aria-invalid and the HTML constraint validation API.
