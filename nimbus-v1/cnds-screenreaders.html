    Screen reader utilities let you include content that is announced by assistive technologies — such as screen readers and Braille displays — while keeping it invisible to sighted users. This is essential for providing accessible labels, section headings, and skip-navigation links that communicate page structure without cluttering the visual layout.

    Two utility classes are available: .visually-hidden permanently removes an element from the visual rendering while keeping it in the accessibility tree, and .visually-hidden-focusable reveals the element only when it receives keyboard focus. Both are CSS-only — no JavaScript is required — and are also exposed as SCSS mixins for use in component stylesheets.

    Note: Read the API Documentation to find all available options and advanced customization.

    Note: To preview components in different themes, click the theme toggle button / in the header navigation bar.

    Basic example

    Apply .visually-hidden to any element you want present in the accessibility tree but invisible on screen. A common use case is a section heading that orients screen reader users but would be visually redundant alongside other design elements. The class uses a clip-based technique that collapses the element to zero visible dimensions without removing it from document flow or the DOM.

    Use .visually-hidden-focusable for elements that should remain hidden until they receive keyboard focus — the canonical example being a skip-navigation link. When a keyboard-only user tabs to the page for the first time, the link becomes visible and allows them to jump past repetitive navigation blocks directly to the main content, satisfying WCAG 2.4.1 Bypass Blocks.

    Both utilities are also available as SCSS mixins (@include visually-hidden and @include visually-hidden-focusable) for applying the same behavior to custom component selectors without adding a utility class to the markup.

    HTML

    <!-- visually-hidden: present in DOM and accessibility tree; invisible on screen -->
<h2 class="visually-hidden">Title for screen readers</h2>

<!-- visually-hidden-focusable: hidden until keyboard focus is received -->
<a class="visually-hidden-focusable" href="#main-content">Skip to main content</a>

    CSS

    // Apply the clip technique to a custom selector
.visually-hidden-title {
  @include visually-hidden;
}

// Reveal element on keyboard focus
.skip-navigation {
  @include visually-hidden-focusable;
}

    Accessibility

    The .visually-hidden and .visually-hidden-focusable utilities use a clip-based CSS technique that removes the element from the visual rendering without removing it from the DOM or the accessibility tree. This is intentional — display: none and visibility: hidden hide content from both sighted users and assistive technologies, and must not be used as substitutes.

    WCAG compliance

    • WCAG 2.4.1 Bypass Blocks (Level A) — Use .visually-hidden-focusable on a skip-navigation link as the first focusable element on every page. This allows keyboard-only users to bypass repeated navigation blocks.
    • WCAG 1.3.1 Info and Relationships (Level A) — Use .visually-hidden headings to provide structural context for screen reader users when a visible heading would be redundant in the design.
    • WCAG 2.4.6 Headings and Labels (Level AA) — Visually-hidden headings still contribute to the page's heading outline, which screen reader users navigate by heading level.
    • WCAG 4.1.2 Name, Role, Value (Level A) — Use .visually-hidden spans to provide accessible names for icon-only buttons and controls where the visible label is an icon alone.

    Section 508 compliance

    Under Section 508 of the Rehabilitation Act (aligned with WCAG 2.0 Level AA), these utilities directly support the following requirements:

    • §1194.22(o) — A method shall be provided that permits users to skip repetitive navigation links. The .visually-hidden-focusable skip link placed as the first focusable element in <body> satisfies this criterion.
    • §1194.31(a) — Applications shall be compatible with assistive technology. Visually-hidden content remains in the accessibility tree and is fully compatible with all major screen readers (NVDA, JAWS, VoiceOver, Narrator).

    For the full specification, see the WCAG 2.1 guidelines and the Section 508 standards.

    API Documentation

    Introduction

    The Nimbus screen reader utilities are CSS-only — no JavaScript initialisation is required. Both .visually-hidden and .visually-hidden-focusable use a clip-based technique: the element is positioned absolutely, scaled to 1×1 px, and its overflow is clipped, so it occupies no visible space while remaining fully present in the DOM and the accessibility tree. This is distinct from display: none, which removes the element from both the visual rendering and assistive technologies.

    Both utilities are defined in utilities.css and are also available as SCSS mixins (@include visually-hidden and @include visually-hidden-focusable) for applying the same behavior to custom component selectors without adding a utility class to the markup. The focusable variant restores the element's natural dimensions and colors on :focus and :focus-within, inheriting from the active theme automatically.

    Usage

    Add .visually-hidden to any element that should be present in the accessibility tree but invisible on screen. Add .visually-hidden-focusable to any focusable element (typically an <a> or <button>) that should reveal itself when focused by a keyboard user.

    HTML
    <!-- Permanent screen-reader-only text -->
<h2 class="visually-hidden">Section heading for screen readers</h2>

<!-- Skip-navigation link — revealed when focused by keyboard -->
<a class="visually-hidden-focusable" href="#main-content">Skip to main content</a>

    CSS classes

    The following classes are defined in utilities.css. They are CSS-only and require no JavaScript.

    Class Element Description
    .visually-hidden Any Clips the element to 1×1 px using absolute positioning and clip-path: inset(50%). The element remains in the DOM and the accessibility tree; sighted users cannot see it. Do not apply to interactive elements — use .visually-hidden-focusable instead so focus styles are preserved.
    .visually-hidden-focusable Focusable (<a>, <button>, tabindex element) Applies the same clip technique as .visually-hidden by default. When the element — or any descendant — receives keyboard focus, all clip properties are reset and the element becomes fully visible. The canonical use case is a skip-navigation link placed as the first focusable element on the page.

    SCSS mixins

    Both utilities are exposed as SCSS mixins for use in component stylesheets when adding a utility class to the markup is not appropriate.

    Mixin Description
    @include visually-hidden Applies the clip-based visually-hidden technique to any custom selector. Equivalent to adding .visually-hidden in markup.
    @include visually-hidden-focusable Applies visually-hidden and adds :focus / :focus-within resets so the element becomes visible when it or a descendant is focused. Equivalent to .visually-hidden-focusable in markup.
    CSS
    // Apply the clip technique to a custom selector
.visually-hidden-title {
  @include visually-hidden;
}

// Reveal element on keyboard focus
.skip-navigation {
  @include visually-hidden-focusable;
}

    Accessibility

    Keep the following requirements in mind when using these utilities:

    • Never use display: none or visibility: hidden as a substitute — both remove content from the accessibility tree and will cause screen readers to skip the element entirely.
    • Place the .visually-hidden-focusable skip link as the first focusable element in the <body> so keyboard users can activate it before any other control.
    • Ensure the href on the skip link points to a valid id on the page (e.g., href="#main-content" paired with <main id="main-content">).
    • Use .visually-hidden text inside icon-only controls to provide accessible names satisfying WCAG 4.1.2 Name, Role, Value.
    • Test with a keyboard-only workflow: press Tab as the first action on the page and verify the skip link appears and functions correctly.

    For the full specification, see the WAI-ARIA Authoring Practices.
