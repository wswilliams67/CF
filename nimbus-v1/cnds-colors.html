    The Nimbus Design System uses a comprehensive, token-based color architecture organized into distinct categories: Brand (Cloudficient corporate identity), Product (per-product palettes for CaseFusion, Hyperlize, and ExpireOn), Surface (UI chrome, panels, buttons), Semantic (status signals such as success, danger, warning, and info), and the full Material Design palette as utility helpers. All color primitives are defined as CSS custom properties in primitives.css and mapped to utility classes for backgrounds (.bg-*), text (.text-*), and links (.link-*). This three-layer token pipeline — primitives → theme mappings → utility classes — means a single class like .bg-success resolves to the correct color in both light and dark contexts without any JavaScript.

    Colors are fully theme-aware. The system supports both light and dark themes via the data-cnds-theme attribute on the root <html> element ("light" or "dark"). Semantic and surface tokens automatically adapt when the theme changes — defined in light.css and dark.css respectively — while brand and product colors remain consistent across themes. Interactive state colors (hover, focus, active, disabled) are derived from their base token and are documented in the component CSS files. For accessibility, color is never the sole means of conveying information; icons, labels, and text descriptions always accompany color-coded UI elements. All documented color pairings meet WCAG 2.1 AA contrast requirements (minimum 4.5:1 for normal text, 3:1 for large text and UI components).

    Note: Read the API Documentation to find all available options and advanced customization.

    Note: To preview components in different themes, click the theme toggle button / in the header navigation bar.

    Chart colors

    Every product carries a ten-step chart palette, exposed as --cnds-chart-color-1…-10 on .chart. A chart on a product surface picks its palette up automatically — no colors option is needed. The step outlined below is the product’s own -500, preserved exactly.

    Theme-aware, and it has to be. Ten steps at a true 10 L* would need the whole 0–100 range, which puts one end in a crush zone: below about L*20 everything is one black on white, above about L*82 everything is glare on #252525. So each theme gets its own band — Light 20–94, Dark 8–82 — at 8.2 L* per step. Slightly tighter than 10, but 8.2 across a band you can see beats 10 across one you cannot. Toggle the theme above to compare.
    These are not the product UI ramps. --cnds-product-*-50…950 are weighted toward the light tints a surface needs: their best ten steps sit only 4.6–6.8 L* apart, which is indistinguishable as chart series. Re-spacing those was not an option either — -200, -300, -400, -700 and -800 are consumed in roughly a hundred declarations across colors, typography, accordion, toolbars, select, navbar, datatable, org-chart and timepicker. Charts get their own scale instead.
    Sequential, not categorical. Right for stacked and single-series charts, where the series have an order. For a grouped chart of unrelated series, pass your own categorical colors — neighbouring bars differing only by shade is not a legend anyone can read.

    Walk the ramp so the largest series sits nearest the page ground: darkest-first on dark, lightest-first on light. A large area is read by its size rather than its contrast.

    Introduction

    The Nimbus Design System provides a comprehensive set of color utility classes for backgrounds, text, borders, and gradients. Colors are built on a design token architecture that flows from primitive values through semantic themes, ensuring consistency across light and dark modes.

    The token pipeline follows this hierarchy: Primitives (raw color values) → Themes (light/dark semantic mappings) → Utility classes (ready-to-use CSS classes). This approach allows a single class like .bg-primary to resolve to different actual colors depending on the active theme.

    Usage

    Via CSS classes

    Apply color utility classes directly to HTML elements. Background classes use the .bg-* prefix, text classes use .text-*, and border classes use .border-*.

    HTML
    <!-- Background color -->
<div class="bg-brnd-blue-500 text-white p-3">Brand blue background</div>

<!-- Text color -->
<p class="text-brnd-green-600">Brand green text</p>

<!-- Product theme color -->
<div class="bg-prod-cf-green-500 text-white p-3">CaseFusion green</div>

<!-- Semantic / theme color -->
<div class="bg-primary text-white p-3">Primary background</div>
<span class="text-danger">Danger text</span>

<!-- Surface color -->
<div class="bg-srfc-dark-400 text-white p-3">Dark surface</div>

<!-- Material palette color -->
<div class="bg-red-500 text-white p-3">Red 500</div>
    Via CSS custom properties

    You can also reference design tokens directly in your custom CSS using CSS custom properties (variables). This is useful when you need colors in contexts beyond simple backgrounds or text.

    CSS
    /* Use primitive tokens directly */
.my-custom-card {
  background-color: var(--cnds-brand-blue-500);
  color: var(--cnds-brand-green-100);
  border: 1px solid var(--cnds-surface-blue-400);
}

/* Use semantic theme tokens (auto-switch light/dark) */
.my-themed-element {
  background-color: var(--cnds-body-bg);
  color: var(--cnds-body-color);
  border-color: var(--cnds-border-color);
}

/* Product tokens */
.casefusion-highlight {
  background-color: var(--cnds-product-casefusion-green-500);
}

    Accessibility

    Color is a powerful communication tool but must never be the sole means of conveying information (WCAG 2.1 SC 1.4.1, Section 508 §1194.21(i)). Every color-coded UI element in CNDS must pair color with at least one non-color cue: an icon, a text label, a pattern, or an ARIA attribute. The status badges in the product example above demonstrate this correctly — each badge combines a background color, an MDI icon, and a visible text label.

    WCAG 2.1 contrast requirements
    Context Minimum Ratio WCAG Level Notes
    Normal text (<18pt / <14pt bold) 4.5:1 AA Body text, labels, badge text
    Large text (≥18pt / ≥14pt bold) 3:1 AA Section headings, large UI labels
    UI components and graphical objects 3:1 AA Borders, icons, focus indicators, chart elements
    Enhanced text 7:1 AAA Target for critical information (error messages, warnings)

    Non-color cue requirements (Section 508 / WCAG 1.4.1)
    • Status badges — pair a background fill with an MDI icon (mdi-check-circle-outline, mdi-alert-outline, mdi-close-circle-outline) and a visible text label.
    • Form validation — in addition to border color changes, display an error icon and descriptive text message below the field.
    • Charts and data visualization — supplement color with patterns, textures, or direct data labels so color-blind users can interpret the data independently.
    • Links vs. plain text — links must be identifiable by more than color alone (underline or other visual cue).
    • Focus indicators — use the --cnds-focus-ring-color token for keyboard focus outlines; never rely on color alone to indicate focus state.

    For the full WCAG 2.1 color guidelines see Understanding SC 1.4.1: Use of Color and Understanding SC 1.4.3: Contrast (Minimum).
